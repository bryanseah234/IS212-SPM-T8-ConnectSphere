# E01-S03 — Hide internal planning information from Attendees

Implements the supplied Release 1 / Sprint 1 story without changing its acceptance
criteria. The attendee identity comes from the signed-in PostgreSQL session,
never a request parameter or a role selector.

## Behaviour

- `/attendee/events` lists only published events with a `registered` registration
  for the current attendee. Waitlisted, withdrawn, unpublished and unregistered
  events are excluded, including direct ID and event-code access.
- `/attendee/events/:id` returns only ID, published name, start/end date and time,
  venue name and location. Notes, booking decisions, reservations and comments
  are not part of the response. Internal planning edits do not change a published
  snapshot until an authorised coordinator republishes it.
- `/internal/planning/:id` calls an API that refuses access and commits an
  `audit_logs` row with actor, target event, attempted identifier, action and time.
  The organiser API also refuses and logs attendee attempts to read planning data.
  Audit failure returns a generic unavailable response without private details.
- Event emails to attendees require a current registration and published snapshot;
  their content is generated from public fields, never internal notification text.
- The UI provides loading, empty, sign-in, denied-access and retry states on desktop
  and mobile. The API returns `Cache-Control: private, no-store`.

## PostgreSQL setup

1. Configure server-only `DATABASE_URL` (or `DATABASE_POOLER_URL`) and `APP_URL`
   with the exact browser origin. Supabase is not used for authentication.
2. Apply all migrations using `npm run db:migrate`, including
   `0004_attendee_visibility.sql`. Serve Vercel functions and frontend on the same
   origin; Vite alone serves only the frontend.
3. Accounts use `users.password_hash` in the salted scrypt format generated by
   `hashPassword` in `accessControl/passwords.ts`. The test seeder now generates
   this format. Existing `seed-sha256` hashes are deliberately rejected; reseed a
   disposable database or use a trusted password-reset/provisioning process.
4. Registrations must exist in `event_registrations`. The general seeder does not
   yet create all registration/booking fixtures; the integration tests create a
   complete isolated fixture automatically.
5. Publish a confirmed event with a confirmed venue using
   `POST /api/events/publish`, JSON `{ "eventId": "<event UUID>" }`, while signed
   in as its assigned coordinator. This explicitly copies the public fields to
   `event_publications`. Unpublished events remain hidden. A coordinator publishing
   UI is outside this attendee story; the protected API is available for it.

Passwords are salted scrypt hashes. Sessions use random opaque tokens, with only
SHA-256 token digests persisted in `auth_sessions`. Cookies are HttpOnly,
SameSite=Strict and Secure in production. Sessions expire after one hour; logout
revokes the database record. Active state, lock state, role and membership are
checked against current database data. Five bad password attempts block login;
account recovery and public account creation remain separate stories. The shared session migration
0003 enforces case-insensitive email uniqueness and must fail for existing
case-duplicate accounts until those are resolved.

The runtime connection must be a trusted server role with access to the tables;
never expose it to browsers. RLS is enabled without browser policies on the
publication/session and relevant planning tables. The unused legacy `auth_subject`
column from migration 0002 is retained to avoid rewriting an applied migration.

## Verification

```sh
npm run typecheck
npm run build
node --import tsx --test backend/tests/eventVisibility.test.ts
TEST_DATABASE_URL='<disposable PostgreSQL URL>' node --import tsx --test --test-concurrency=1 backend/tests/attendeeVisibility.integration.test.ts backend/tests/eventVisibility.integration.test.ts
npx playwright test tests/e2e/attendee-events.spec.ts tests/e2e/client-events.spec.ts
python3.12 scripts/check.py
```

Run integration suites sequentially because migration setup uses shared PostgreSQL
extensions. Each suite creates and removes an isolated schema. Use a disposable
DB, never production. Browser checks use mocked API responses; PostgreSQL/API
integration tests exercise actual password verification, session lookup, SQL,
publication, registration filtering and persistent audit writes.

Before release, deploy with the actual PostgreSQL configuration and check sign-in,
the published event list and direct internal URL denial using a real test attendee.
Review the audit row in trusted database administration. Human PR review and the
live deployment smoke test remain required; local tests do not certify deployment.
